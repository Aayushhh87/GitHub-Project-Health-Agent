==================================================
1. CODE QUALITY ANALYZER
==================================================

Create/update:

backend/app/analyzer/quality.py

Implement a deterministic code-quality analyzer.

For Python files:
- Detect syntax errors using Python AST parsing.
- Detect very long files.
- Detect very long functions/methods.
- Detect excessive nesting where reasonably possible.
- Detect TODO/FIXME comments.
- Detect broad exception handling such as "except Exception".
- Detect obvious unused imports if practical.
- Use radon if available for cyclomatic complexity.
- Use ruff if available, but DO NOT make the whole application fail if ruff is unavailable.
- Gracefully support repositories that do not contain Python.

For JavaScript/TypeScript:
- Perform lightweight static checks without executing repository code.
- Detect very long files/functions where practical.
- Detect TODO/FIXME comments.
- Detect obvious console/debug statements.
- Detect overly large source files.
- Do not require Node.js tooling to be installed.

For other languages:
- At minimum perform generic checks:
  - file size
  - line count
  - TODO/FIXME
  - obvious debug statements where safely detectable

Every quality finding must contain:
- severity
- category = "Code Quality"
- title
- file
- line if available
- evidence
- recommendation

Do not report every normal file as a finding.
Only report meaningful issues.

==================================================
2. SECURITY ANALYZER
==================================================

Create/update:

backend/app/analyzer/security.py

Implement deterministic security scanning.

Detect likely hardcoded secrets using safe regex/pattern matching, including examples such as:
- API keys
- tokens
- passwords
- private keys
- common cloud credentials
- GitHub tokens
- JWT-like strings where reasonably detectable

Also detect common insecure patterns where practical:
- hardcoded passwords
- hardcoded credentials
- dangerous eval/exec usage
- Python subprocess calls with shell=True
- use of pickle.loads / pickle.load
- insecure HTTP URLs in configuration/source where relevant
- overly permissive CORS such as allow_origins=["*"] in backend code
- obvious SQL string concatenation/interpolation patterns
- disabled TLS verification such as verify=False
- debug mode enabled in production-like configuration where detectable

IMPORTANT SECURITY RULE:
NEVER send raw secrets to an LLM.
For secret findings, mask the detected value.

Example:
BAD:
evidence = "sk-123456789abcdef..."

GOOD:
evidence = "Possible API key detected: sk-12********"

Never print secrets to logs.
Never return complete secrets in API responses.

Every security finding must contain:
- severity
- category = "Security"
- title
- file
- line if available
- evidence
- recommendation

Severity guidance:
- CRITICAL: private keys, highly sensitive credentials, severe credential exposure
- HIGH: API tokens, passwords, cloud credentials, serious insecure execution
- MEDIUM: dangerous configuration or risky coding pattern
- LOW: minor security weakness

Avoid excessive false positives.
Use confidence-aware patterns where possible.
